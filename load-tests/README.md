# FlashDrop load tests

The primary script starts one iteration from each virtual user, so 10,000 VUs make exactly 10,000 unique customer requests. It checks accepted and stock-rejected counts, response latency percentiles, final inventory, and overselling count, and writes a measured JSON report to `load-tests/results/flash-sale-report.json`.

Before a run, start the local stack and reset the demo database to 100 units. The script refuses to start if the current stock differs from `INITIAL_STOCK`. For a local run, set the API rate limit above the request count (for example `RATE_LIMIT_MAX=15000`) so the result measures database contention rather than the local per-IP safety limit.

~~~sh
BASE_URL=http://localhost:3000 INITIAL_STOCK=100 VUS=10000 pnpm load:test
~~~

On PowerShell, set ` $env:BASE_URL `, ` $env:INITIAL_STOCK `, ` $env:VUS `, and ` $env:RATE_LIMIT_MAX ` before invoking `pnpm load:test`.

`idempotency.js` sends concurrent requests with one shared user and key to verify replay behavior. `worker-throughput.js` produces orders at a configurable rate, waits for the worker to drain those events, and prints processed count and final consumer lag. Use a separate test database with stock above the planned accepted request count.

~~~sh
BASE_URL=http://localhost:3000 WORKER_METRICS_URL=http://localhost:9464 INITIAL_STOCK=20000 RATE=500 DURATION=30s pnpm exec k6 run load-tests/worker-throughput.js
~~~

No benchmark numbers are checked into this repository. A valid report must come from an actual run and should include the host CPU/memory, Docker engine version, database/broker configuration, API replica count, worker count, and the JSON file generated by k6.
